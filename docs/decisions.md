# Решения по проекту Linager

## Принятые решения
| Тема | Решение |
|---|---|
| Название | Linager |
| Язык и сборка | Go, один бинарник `linager` с ролями server и agent |
| Платформа | Debian 12 и 13, Ubuntu 22.04, 24.04 и 26.04 LTS (Debian 11 снят с поддержки); amd64, а для агента ещё и arm64 (Raspberry Pi 4 с 64-разрядной ОС). Сервер на arm64 не поддерживается |
| Репозиторий | GitHub, публичный, лицензия Apache-2.0 (допущение, можно сменить) |
| Установка | Скрипт `install.sh` скачивается с GitHub, мастер сразу спрашивает Клиент или Сервер |
| БД | Только локальный PostgreSQL, ставит и настраивает установщик, внешняя БД не поддерживается |
| Администраторы | Несколько пользователей с одной ролью «администратор» (0.1.40); отдельные роли позже |
| TLS и доступ | Самоподписанный, Let's Encrypt, свой сертификат, обратный прокси на этом же или соседнем сервере |
| Обновления агентов | Через сервер Linager (сервер кэширует релизы с GitHub), не напрямую |
| Обновления сервера | CLI и админка, с бэкапом БД, миграциями и автооткатом |
| Хранение метрик | 5 с: 1 час; 1 мин: 7 дней; 5 мин: 90 дней; 15 мин: 180 дней; 1 час: 360 дней (последние два уровня выбраны по просьбе «ещё 180 и 360», шаг агрегации предложен) |
| Языки интерфейса | Русский (основной) и английский |
| Шрифт | Medeo: Mono для текста, Pixel для заголовков и подписей, лицензия SIL OFL 1.1 |
| Значки | Pixelarticons 2.4.2 (MIT), лицензия лежит рядом с данными: `web/src/lib/ui/pixelarticons-LICENSE.txt` |

## Как работает привязка клиента
1. На клиенте: адрес сервера, генерация ключа Ed25519, вывод ключа и отпечатка.
2. В админке появляется подключение в статусе «ожидает подтверждения».
3. Админ вводит ключ, подтверждает. После этого связь по mTLS, подписанные сообщения.
4. Дополнение к исходной идее: агент проверяет отпечаток сервера, показывается короткий код сверки на обеих сторонах.

## Подтверждено владельцем (14 ноября 2026)
- Debian 12 и 13 (11 не поддерживается). Лицензия Apache-2.0. Шаги агрегации 15 минут (180 дней) и 1 час (360 дней).
- Версия агента в списках показывается рядом с версией Debian.
- Владелец репозитория: GitHub `bolgov0zero`, репозиторий `bolgov0zero/linager` (заглушка `OWNER` заменена).
- Порты Linager (агентов и админки): значений по умолчанию нет, мастер спрашивает их обязательно; в неинтерактивном режиме флаги обязательны. Клиенты подключаются на отдельный порт напрямую, не через прокси. Публичный порт админки за Caddy: 443 (порт самого прокси).
- Поддержка Ubuntu 22.04, 24.04 и 26.04 LTS добавлена (14 ноября 2026). Установщик универсальный для семейства Debian/Ubuntu. Сеть на Ubuntu управляется через netplan, на Debian через ifupdown (бэкенды сети).
- Режимы админки в мастере: (1) «Caddy»: установщик ставит Caddy на этот же сервер, сертификат Let's Encrypt для домена, порт 443; (2) «Обратный прокси»: установщик ничего не ставит и не настраивает, только запрашивает порты. Адрес прослушивания `0.0.0.0` и доверенные прокси `0.0.0.0/0` заданы по умолчанию и не спрашиваются (по решению владельца); в `server.yaml` их можно сузить. Режим подходит и для закрытых сетей со своим прокси.
- Конфликт ufw и nftables на Ubuntu: в 0.1 только предупреждение во вкладке «Файрвол».
- Тестовая среда: две машины в локальной сети владельца, плюс контейнеры в CI.
- Ключ подписи релизов создаёт владелец, секрет `MINISIGN_KEY`.
- Подпись релизов: на усмотрение исполнителя, см. `docs/architecture.md` (minisign-совместимая Ed25519).
- TLS в первых релизах: только режим обратного прокси (без сертификата на стороне админки), Caddy как основной пример. Тот же режим для локальных и закрытых корпоративных сетей.
- Оповещения (Telegram, email) в первую версию не входят.
- Установщик: красивый, интерактивный, пошаговый, с прогрессом по этапам, без лишнего вывода; экран очищается перед запуском.

## Windows-агент (18 ноября 2026)
- Решение владельца: агент для Windows x64 (Windows 10/11, Server 2016+), только то, что работает сразу: метрики и инвентаризация, процессы, службы, журнал событий, терминал (ConPTY), файлы, перезагрузка. Сервер остаётся на Linux. Установка через MSI (WiX v4), выпуск первой версии в канал beta (`v0.3.0-beta.1`).
- В beta не входят: самообновление агента (обновление новым MSI поверх; панель показывает «новый MSI»), установка по ссылке с одним подтверждением (привязка по ключу и проверочному коду), apt, файрвол, сеть, пользователи, Docker, диск, безопасность, arm64, подпись кода. Дальше только по запросу владельца (см. память проекта: не растить проект без запроса).
- Новые зависимости: `github.com/shirou/gopsutil/v4` (метрики и процессы в Windows). ConPTY сделан на `golang.org/x/sys/windows` без отдельной библиотеки.
- Платформа CLAUDE.md расширена: Windows x64, только агент.
- Обновление Windows-агента из панели (по запросу владельца, 18 ноября 2026): подписанный exe заменяет запущенный (переименованием), откат разовой задачей планировщика от SYSTEM через 70 секунд, как таймер systemd у Linux. MSI остаётся для первой установки. Агенты beta.1–beta.3 обновляются один раз новым MSI.

- Рабочий стол Windows в браузере (по запросу владельца, 18 ноября 2026): RDP через туннель агента и браузерный клиент IronRDP (WebAssembly), прокси RDCleanPath на Go в сервере, без внешних демонов (`guacd` отвергнут). Окно и вкладка как у терминала, пункт в меню плитки, Ctrl+Alt+Del и меню «Ещё» на панели окна, текстовый буфер обмена; файлы через проводник. Не входят: звук, принтеры и диски, Kerberos, запись сеанса, рабочий стол Linux. Право «desktop» у оператора выключено по умолчанию. CSP расширена `wasm-unsafe-eval` и `data:` в `connect-src`.
- Помощник Windows (по запросу владельца, 19 ноября 2026; бета-канал, 0.4.0-beta.1): вид и управление консолью или сеансом RDP, как Aspia и Radmin. Своё решение на Go без внешних демонов и без cgo: помощник в сеансе (тот же `linager.exe`) снимает экран через GDI и шлёт плитки JPEG; настоящего видеокодека нет, «битрейт» это лимит трафика с самонастройкой качества. Запроса согласия у пользователя нет (корпоративная сеть, согласия подписываются при приёме на работу); вместо него отдельное право «Помощник» (у оператора выключено), аудит каждого открытия и значимых изменений. Помощник работает от SYSTEM с первой версии: так будут работать экран блокировки и UAC. Этап 1: рабочий стол вошедшего пользователя, основной монитор, курсор рисуется в кадре; этап 2 (по отдельному решению): экран блокировки и UAC, Ctrl+Alt+Del, буфер обмена, выбор монитора. Вкладка «Управление» (цвета, частота кадров, лимит трафика, включение и выключение RDP). Не входят: звук, передача файлов, запись сеанса, подключение к отключённому сеансу.

- Вид «Пульт» (по запросу владельца, 19 ноября 2026; бета-канал): третий вид дашборда с сайдбаром серверов, вкладками сеансов (терминал, RDP, Помощник) и плавающими окнами Файлов. Название выбрано владельцем (из «Пульт», «Рабочее место», «Операторская», «Сеансы»). Решения: на телефоне вида нет; сеансы принадлежат «Пульту», а не странице сервера, и остаются в фоне при уходе в «Карточки» или «Карту»; скрытый Помощник ставится на паузу (кадр `Pause`), RDP нет; окна сворачиваются в область «Окна» внизу сайдбара; запоминаются вкладки, режим, группы и окна Файлов. Не входит: терминал, переживающий закрытие вкладки (нужна постоянная оболочка на агенте), восстановление папки терминала и папки окна Файлов.

## Что не входит в первую версию
- Архитектура arm64.
- Внешний PostgreSQL.
- Несколько пользователей и роли (заложить в модель данных, реализовать позже).
- Оповещения.
- Режимы TLS «самоподписанный», «Let's Encrypt», «свой сертификат» для админки (заложить в конфиг, реализовать позже).

- Ключи (по запросу владельца, 20 ноября 2026; бета-канал 0.9.0-beta.1): личный зашифрованный файл с логинами и паролями у каждого пользователя панели, пункт «Ключи» в меню верхней строки. Файл хранится у человека, не на сервере и не в базе: Argon2id (64 МиБ, 3 прохода) и AES-256-GCM, всё в браузере (`@noble/hashes`, `@noble/ciphers`, чистый JavaScript: работает по HTTP без `crypto.subtle`, без WebAssembly и правки CSP). Файл открывается один раз за вкладку и живёт расшифрованным только в памяти страницы (ни `localStorage`, ни IndexedDB: единый способ для Chrome и Safari, который не требует запоминать путь к файлу); автоблокировка, предупреждение о несохранённом, забывание при выходе. Запись: название, тип (RDP, UAC, любой), привязка к нескольким группам и серверам (только порядок в списках, не защита), логин, домен, пароль, заметка. Этап 1: подстановка в форму RDP (пароль остаётся в браузере и идёт в CredSSP клиента). Сервер и агент не менялись. Этап 2 (по отдельному решению): ввод в запрос UAC и на экран входа Windows (новый кадр «напечатать текст» без буфера обмена, только пока активен рабочий стол Winlogon, кнопка с ключом в Помощнике). Не входят: синхронизация между устройствами, общий файл команды, история, вложения.
- Ввод ключа в UAC и на экран входа Windows (по запросу владельца, 20 ноября 2026; 0.9.0-beta.3): кнопка с ключом в Помощнике, пока активен рабочий стол Winlogon; логин, пароль или вход целиком (логин, Tab, пароль, Enter). Новый кадр `Type`: текст печатается символами (`SendInput` Unicode), без буфера обмена; агент печатает только при активном Winlogon и проверяет это в момент ввода. Пароль идёт через сервер в памяти (шифрование «браузер → агент» отложено); в аудит попадают сеанс, название ключа, число символов, без текста; не больше 60 вводов за открытие. Права: как у Помощника. Только Windows. Не проверено на живой Windows: ввод на рабочем столе Winlogon.
## Итоги реализации (0.1)
- Платформы: Debian 12/13, Ubuntu 22.04/24.04/26.04 (проверено на Debian 13; остальные ждут проверки на живых системах).
- Реализовано: сервер и агент, привязка с подтверждением, метрики и история, терминал, службы, apt, процессы, журналы, файлы, сеть и файрвол с откатом, Docker, подписанные обновления сервера и агентов, бэкапы, журнал аудита, установщик (TUI и без вопросов).
- Не вошло по решениям владельца или ограничениям: оповещения; редактирование сети на netplan (только просмотр); несколько пользователей и роли (заложены в схему); режимы TLS админки без Caddy/прокси.
- Ключ подписи релизов создан, секрет `MINISIGN_KEY` хранится в GitHub Actions; открытая часть вшита в бинарник и `install.sh`.
- Порт приложения (по запросу владельца, 23 ноября 2026; бета-канал 0.10.0-beta.1): третий порт сервера, прямой TLS 1.3 с сертификатом порта агентов, тот же API, что у админки; заголовки обратного прокси на нём отбрасываются. Мастер спрашивает его всегда (`--app-port`, без значения по умолчанию), `server.yaml` получает `app.listen`; у ранее установленного сервера порт не задан и вводится в «Настройки» → «Подключение». Значения портов из панели хранятся в таблице `settings` (ключ `connection`) и сильнее `server.yaml`: служба не пишет в `/etc/linager`. Повторная установка с `--force` стирает ключ, ответы мастера главнее. Приложение Linager (Wails v3) станет единственным интерфейсом, `web/` заморожен, кроме этого раздела.
- Смена порта агентов из панели (по запросу владельца, 23 ноября 2026; 0.10.0-beta.1): агенты переезжают сами. Сервер открывает новый порт и держит старый; подключённым агентам и агентам, вернувшимся на старый порт, шлёт подписанное сообщение `server.move` (только порт, хост прежний); агент пробует новый адрес первым, после трёх неудач возвращается на старый (откат на стороне агента, как у сети и файрвола) и час игнорирует тот же порт. Старый порт закрывается сам, когда все агенты перешли (`servers.last_port`), или кнопкой с подтверждением. Агент понимает переезд с 0.10.0-beta.1; пока в сети есть более старый, порт агентов менять нельзя.
- Приложение для рабочего стола (по решению владельца, 23 ноября 2026; этап 1, бета-канал): Wails v3 (v3.1.0), отдельный модуль `app/`, единственный интерфейс в будущем; `web/` заморожен (без правок и новых функций), после релиза с пометкой «устарел» удаляется вместе с вопросом установщика «Доступ к админке». Дизайн по макету `docs/design/redesign/` (вариант A), значки Lucide, шрифты Medeo Sans и Medeo Mono; логотип текущий. Первичная настройка остаётся в установщике (CLI), приложение подключается к готовому серверу. Мобильный клиент решаем позже. Каждое плавающее окно макета в приложении отдельное нативное окно.
- Устройство приложения: в процессе поднимается локальный сервер на `127.0.0.1` (случайный порт, случайный токен в каждом пути, проверка `Host` против DNS rebinding), окна открывают его адрес. Он отдаёт интерфейс, проксирует API сервера по TLS с закреплением отпечатка сертификата (доверие при первом подключении, как SSH, отпечаток сверяет человек) и даёт то, чего нет у веб-страницы: профили серверов, связку ключей (Keychain, Credential Manager, Secret Service), открытие окон. Cookie сессии хранится в Go и до страницы не доходит. Страница не зависит от Wails, поэтому интерфейс можно открыть в браузере (`-headless`).
- Известные ограничения этапа 1: вход по passkey в приложении недоступен (адрес окна другой, чем у сервера, WebAuthn не сработает, нужно отдельное решение); сборка под Linux требует native-раннера с WebKitGTK 6.0, на Debian 12 и Ubuntu 22.04 не проверена; окна, кроме главного и терминала, и страница сервера в приложении пока не сделаны.
