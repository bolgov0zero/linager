# Linager security

## Threat model
The Linager server manages servers with root privileges, so compromising the server is equivalent to compromising all clients. The protection is designed on the assumption that the agent channel may run through an untrusted network. The interface of the server is the Linager application: it connects to the application port over TLS 1.3 and pins the certificate (a person confirms the fingerprint at the first connection). There is no web panel and no reverse proxy is needed.

## What is protected and how
- **Agent channel:** TLS 1.3. The client-port certificate is self-signed, and the agent pins its fingerprint. After enrollment, mutual TLS (mTLS) is used with a certificate issued by the server's internal CA (valid for one year; the agent renews it over the channel by itself). Every message is signed with Ed25519 (the agent key and a separate server command-signing key), and there is a sequence counter and a time window against replays.
- **Agent enrollment:** the agent verifies the server fingerprint (the `--fingerprint` flag or explicit confirmation), both ends show a **verification code**, and the administrator enters the **enrollment key** from the agent's console. Five wrong keys reject the request; requests are rate-limited and expire after 15 minutes.
- **Install by a link:** the token of a link (128 bits) is shown once and only its hash is stored; a link has a lifetime, a number of uses and an optional list of networks, and can be revoked. The command pins the key of the server (`--pinnedpubkey`), and the script checks the binary against the signed manifest. A request that came by a link waits for confirmation by default; automatic approval is a switch on the link. Every step goes to the audit journal. More: [install.md](install.md).
- **Install over SSH:** the server connects outward, so: a person confirms the host key; the password, the key and the `sudo` password live only in memory while the install runs and never reach the log or the audit; a password is accepted over TLS only (the application port is encrypted); loopback, link-local (cloud metadata) and multicast addresses are refused; the range can be narrowed in `ssh_install.allowed_networks`; the number of installs and attempts is limited. On a failure the agent is removed from the host.
- **Administrator login:** argon2id passwords, brute-force protection (per IP and per login, with growing delays), one-time TOTP codes cannot be reused, sessions are stored in the database (only a hash of the token is kept), `HttpOnly` cookie, `SameSite=Strict`, `Secure` over HTTPS, CSRF token on every state-changing request, `Origin` check for WebSocket.
- **2FA:** TOTP is enabled in the application (Settings → Profile). The `admin.require_totp: true` parameter in `server.yaml` blocks the entire interface until the administrator enables 2FA. Sign-in has two steps: login and password first, and only if the user has 2FA enabled the application asks for a code. A correct password without a code creates no session and does not count as a failed attempt; a wrong code does.
- **Recovery codes:** enabling 2FA issues 10 one-time codes (only hashes are stored, shown once). A recovery code is entered instead of the code from the app and is burned; new ones are generated in Settings → Profile (the password is required) and the old ones stop working.
- **Passkeys (WebAuthn)** were removed in 0.10.0-beta.17: the application could not use them (the address of its window differs from the address of the server). Sign in with the login, the password and 2FA.
- **Ending SSH sessions:** on the Security tab an administrator can end a remote session or all sessions of a user. The action is confirmed, the agent ends only sessions from its own list (`loginctl terminate-session`), and the entry goes to the audit log with the user and the address.
- **fail2ban, keys and disk cleanup:** installing and configuring fail2ban, banning and unbanning addresses, removing a key from `authorized_keys` and cleaning the disk need a confirmation on the server (`confirm`) and the confirmation flag on the agent, and are written to the audit log. The address of the administrator, loopback and the addresses of the exceptions list cannot be blocked. The agent accepts only names and addresses it has checked itself: the `authorized_keys` file comes from its own list for the user, the cleanup targets are chosen by the agent and not by the browser; a copy of the file is saved before a key is removed. The fail2ban files of the administrator are never rewritten, the settings of the panel live in `/etc/fail2ban/jail.d/linager.conf`.
- **Roles.** An administrator has full access. An operator works only on the servers and with the modules the administrator gave (servers are picked one by one or as a whole group: a server added to the group later is available at once). A module is closed as a whole, on every server of the operator. An operator does not change the settings of the panel (users, updates, the audit log, snippets, groups), does not add or delete agents and does not reboot servers. An auditor only looks at the dashboard, the overview and the metrics of the chosen servers and changes nothing. Both can use their own profile (password, 2FA, passkey). The server checks the rights on every request (the browser only hides buttons): every route has an access rule and a test makes sure a new route does not stay without one. A server the user has no access to does not exist for them (404); a closed module gives 403. A change of the rights works at once, without a new sign-in. An administrator cannot change their own role or demote the last administrator; creating a user and changing a role or access are written to the audit log. The modules Terminal, Files, Network, Firewall, Security and Docker give the access of root on the host: an operator with the terminal can delete the agent or add their own key, so the panel marks them with a warning and they are off by default.
- **Users:** you can add users, change your own password (the other sessions end), reset the password and 2FA of others. You cannot delete yourself. All of this is written to the audit log.
- **Sign-in rate:** `admin.login_rate` in `server.yaml` (attempts per minute per address, default 10).
- **Headers:** a strict Content Security Policy (scripts only from the same origin; `'unsafe-inline'` styles are required by the xterm.js terminal), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, COOP and CORP, HSTS over HTTPS.
- **Dangerous actions:** stopping `ssh` and `linager-agent`, rebooting, deleting files, killing processes, firewall and network rules, and updates all require explicit confirmation. The server sets the confirmation flag only after the administrator responds; an agent rejects such commands without the flag.
- **Server access:** in the application, in Settings → Server access, you can turn on a white list (whatever is not listed is refused) or a black list (whatever is not listed is allowed) by the address of the connection (addresses, networks and DDNS names). The application port is direct, `X-Forwarded-For` is dropped on it. A restriction that would lock you out cannot be saved; if access is lost anyway, run `linager access reset` on the server. The restriction applies to the application port only, the agent port is not affected. The journal of the connections (sign-ins, refused requests) is kept for 30 days. See [access.md](access.md).
- **Rollback:** network and firewall changes are applied with a 30-second timer on the agent. Without confirmation (including when the connection is lost), the settings roll back automatically; the change journal survives an agent restart.
- **Audit log:** all administrator actions (login, enrollment, commands, edits, updates, opening and closing a terminal with the data volume) are recorded with the connection address and the address from `X-Forwarded-For`. Keystrokes in the terminal are not recorded.
- **Updates:** releases are signed (minisign, Ed25519), and the public key is embedded in the binary. The manifest, checksum, and signature are verified on the server and on the agent before replacement; a database copy is made before an update; the binary is restored if the update fails.
- **Permissions:** secrets (`server.yaml`, keys, backups) have permissions 600. The server service runs as the `linager` user with systemd restrictions (`ProtectSystem=strict`, `NoNewPrivileges`, address family filters, an empty capability set except for binding ports). Privileged operations (updates) are performed by a separate service.
- **Database:** only a local PostgreSQL, `scram-sha-256`, and a random role password. The installer refuses to continue if PostgreSQL listens on anything other than localhost or allows trust/md5 over TCP.

## What the administrator should do
1. **Enable 2FA** and, if possible, set `admin.require_totp: true`.
2. **Restrict the application port** with a white list (your networks or a VPN) in Settings → Server access, and open it in the firewall only where it is needed.
3. Open the client port (`agents.listen`) only for the networks that need it.
4. Store backups as secrets: they contain the CA keys.
5. Disable unneeded agent modules in `/etc/linager/agent.yaml` (the terminal and file manager give root access to the entire host).

## Known limitations of version 0.1
- All users have one role, "administrator", with full access (including the terminal and files as root); roles such as "observer" do not exist yet, the data schema is ready for them.
- The terminal and file manager run as the agent's root user.
- Network editing on Ubuntu (netplan) is disabled: view only.
