# The iOS application

A separate native iPhone application (SwiftUI), not a wrapper around the web. The first stage is **the dashboard only**, read-only. Editing the dashboard, folders and tags, the console, users and the other modules are not in it; the management features are the terminal and the Assistant (the remote desktop, RDP, is not there yet). The source is in `ios/`, the mockup of the screens in `docs/design/ios/index.html`.

## What it does

- Connects to a server by address and application port. The certificate is pinned on the first connection (the way SSH remembers a host key): the application shows the fingerprint, the person compares it with the server and confirms.
- Signs in with a login and a password, then a TOTP code or a backup code as a second step.
- **The page of a server** (a tap on a row of the Dashboard, or a long press on a server in the Console → "Server page"; the first stage, read only): at the bottom the system tab bar with **Overview**, **Metrics**, **Files** and **More**. Overview: the state and badges, rings of the CPU, memory and disk, the network (the rates and a chart of the last hour), "Needs attention" (failed services, reboot, updates, Docker images), the facts about the system (each on one line), a note with Markdown. Metrics: the period (1 h, 24 h, 7 d, 30 d) and the charts of the CPU, memory, network and disk with the least, the average and the most, the events of the period; a tap on a chart shows a tooltip with the time and the values, the "…" menu switches whether all the charts share it. **Files** is an ordinary page of the server: a stack of folders, over the list the way to the folder as chips (a tap jumps to any folder on it), the order (by name, date, size), the hidden files, a search in the folder, quick places (/etc, /var/log…), the last folder is remembered for the server; a tap on a file downloads and shows it (Quick Look). The "…" menu of a row (also a long press) gives: "Edit" (a text editor, files up to 1 MB; the save sends the time of the version that was read, and if the file was changed on the server meanwhile the application asks: overwrite with yours or reload; a tab button above the keyboard, a guard against closing with unsaved text), "Share", "Rename", "Copy to…" and "Move to…" (a folder picker; if the name is taken there: keep both or replace), "Permissions" (the nine bits as a grid of owner, group, others × read, write, run, the special bits setuid, setgid and sticky, the octal number, the owner and the group, "apply to everything inside" for folders; system folders are shown only, the special bits are confirmed), copying of the path and the name, "Delete" (confirmed; a swipe left too). The "+" button on top: "New file" (opens in the editor at once), "New folder", "Upload files…" (from the Files app, several at once, with progress; up to 512 MB each) and "Upload photos and videos…" from the library. The tab "Files" is there for an administrator and for an operator with the module "Files"; the server checks the rights to the actions. The data of the page (overview, metrics, the list of files) is refreshed every 5 seconds. "More": the buttons to connect (terminal, Assistant, RDP) and the list of the other sections (services, processes, Docker, logs, disk, updates, network, firewall, security, users), which come in the next stages.
- **Two modes** (the standard tab bar at the bottom, a floating glass one on iOS 26): the **Console** and the **Dashboard**. The application remembers the last mode. The console is a bare list to connect from: the tree of folders of any depth (a tap folds a folder, the number at the right counts the servers inside, nested ones included), a server has a coloured state dot and a system badge as a mark with no text (Windows blue, Linux green, as in the desktop application). The first row of the list is the system segmented switch of the **kind of connection** (Terminal, RDP, Assistant), remembered too; a tap on a server opens it that way, a long press offers the others. A server without that kind of connection is not shown, and a folder with no suitable server is not shown either. The rules are those of the desktop application: the terminal for every server, the Assistant for Windows and for Linux with a graphical console, RDP for Windows while the remote desktop is on. RDP is not in the application yet: its segment is grey and a tap explains it. The "…" menu has a filter by system (All, Windows, Linux) and by status (All, Online, Offline), and "Expand" and "Collapse all folders"; while a filter is on the menu symbol is filled. A search by name, folder and system gives a plain list with the path of folders. The mode, the kind, the filters and the folded folders are kept on the phone.
- The dashboard: four summary tiles (online, attention, updates, CPU), the segment "All / Problems / Offline", a search by name or address, folders as sections (a subfolder is named by its path), two layouts (rows, and cards with a CPU chart), an order and a folder filter, pull to refresh.
- State badges are the compact ones only, as in the desktop application: a symbol and a number (failed services, reboot, updates, Docker images, agent), a word only for "No connection". Tags are letter squares; the full names and the meaning of the badges are in the long-press menu of a row (which also copies the name and the address).
- Live data: the stream `api/live` refreshes the dashboard and is opened again when it breaks. In the background the stream is closed; on return the data is asked for again.
- Without a connection to the server the last received data is shown with its time.
- **The terminal** (long-press a server row → "Terminal"): a shell on the server full screen, the SwiftTerm emulator, its own key bar above the keyboard: a floating glass capsule like the buttons of the top bar (Esc, a sticky Ctrl, Tab, arrows that repeat while held, the signs `~ | / - \ ` [ ] { }` and more, Home, End, PgUp, PgDn, Del, F1–F10; it scrolls sideways), and a separate round capsule at its right that hides the keyboard. A pinch changes the font size (6–22 pt, remembered), a two-finger double tap returns 11 pt. The item is there for an administrator and for an operator with the module "terminal"; it is disabled for an offline server. The rights, the limit of terminals per server and the audit journal are those of the desktop application; the terminal asks for no Face ID of its own. When the application is left, the connection is kept for about 30 seconds and then closed (the agent has no persistent shell, so what was running is interrupted); the screen stays for copying and there is a "Connect again" button. Two buttons at the top right: **snippets** (the commands saved on the server: a tap types and runs one, a swipe left only types it without the Enter; they are made in the desktop application, a run goes to the audit journal) and **user** (a shell as another account of the server: its people and root; choosing one closes the current shell, clears the screen and opens a new one, so that its prompt is the first line; the button is there when the account may see the users of the server). Links in the output are not opened.
- **The Assistant** (long-press a server row → "Assistant"; for Windows and for Linux with a graphical console): the screen of the computer over the whole phone. On connecting the phone turns to landscape by itself and back to portrait when closed. The picture is put together from JPEG tiles and fitted to the height. A glass panel at the top: close, keyboard, keys (Ctrl+Alt+Del, Win, Alt+Tab, task manager, copy and paste), mouse, scale, clipboard, monitor (when there are several), quality and statistics, and "Type on the sign-in screen" on a sign-in screen. The panel folds with the arrow into a round button that can be dragged (it sticks to the edge); it folds by itself when the keyboard is open. Touches: a tap is a left click, a long press or a tap of two fingers a right click, a double tap whose second touch is held and moves is a selection or a drag with the left button held (a text is selected, a window is moved; a quick second tap is a double click), two fingers up and down the mouse wheel (or, when the picture is zoomed and does not fit, they move the picture), a pinch the scale (the picture cannot be made smaller than "fit the screen"). The menu "Mouse" has a switch "Selection mode": while it is on, a finger holds the left button from the moment it touches (a text is selected, a window is moved), a tap is still a click. The mouse has two modes: "direct touch" (the pointer is under the finger) and "touchpad". Keyboard: Latin letters and digits go out as keys of the US layout, everything else (Russian and other alphabets) through the clipboard of the computer and Ctrl+V; above the keyboard a glass bar with Esc, Ctrl, Alt, Win (sticky), Tab, arrows, signs, Home, End, PgUp, PgDn, Ins, Del and F1–F12. "Quality" changes the picture settings of this computer on the server (shared with the desktop application). Only the console session, no sound and no file transfer. Rights: an administrator and an operator with the module "assistant"; the open and the close go to the audit journal.
- **The remote desktop (RDP):** the kind "RDP" in the Console (for Windows while the remote desktop is on), or a long press → "Remote desktop". A sign-in form: the Windows login, password and domain, or "From a key" (keys of the type RDP and "Any", as in the desktop application). The password is kept nowhere, only the login is remembered for the computer. Then the same screen as the Assistant: landscape, the picture fading in, the panel with keys, mouse (direct touch and touchpad), scale, the keyboard with scrolling at the edges. Text of other alphabets goes as characters, with no clipboard. Ctrl+Alt+Del on the remote desktop is Ctrl+Alt+End. The RDP protocol is a native library written in Rust ([IronRDP](https://github.com/Devolutions/IronRDP), `ios/rdp`, pinned to a commit); it talks to the server over RDCleanPath on the same pinned WebSocket (`api/servers/{id}/desktop`), and the server keeps the TLS to Windows. The first version: the picture, the mouse, the keyboard; no clipboard, no sound and no change of the resolution to the window. The picture is asked for compressed, as the browser client does (16 bits, the codecs of the server, the graphics pipeline).
- **Scrolling at the edges with the keyboard up:** the keyboard covers the picture, so it stands still, and when the pointer (the touchpad one, or a finger held in the zone) comes to the edge of the part above the keyboard, the picture scrolls that way, faster nearer the edge, as the "scroll at the edges" of the desktop application. Two fingers can still move it by hand.
- **The device and its confirmation** ([devices.md](devices.md)): at its first connection to a server the application makes a secret token of the device (in the Keychain, `AfterFirstUnlockThisDeviceOnly`, one for each server; "Forget server" erases it) and sends it in the header `X-Linager-Device` with every request, WebSockets included (the terminal, the Assistant, RDP, the stream of events), together with `X-Linager-Client` (the platform, the version and build of the application, the version of iOS, the model like `iPhone18,1`). The server lists the device in Settings → Devices of the desktop application. If "Confirm devices" is on there, after the sign-in the screen **"Waiting for approval"** (with a timer) takes the place of the dashboard: every three seconds the phone asks "who am I" (the only thing allowed) and goes on to the dashboard by itself when an administrator approves. A refused or removed device goes back to the sign-in screen with an explanation. The application waits for the approval after a restart too. If the server answers that the application must introduce itself with a device (`device_required`), update the application.
- **Keys** ("Account" → "Keys"): the same personal `.lvault` file as in the desktop application ([keys.md](keys.md)). The file is not copied into the application: you pick it in Files (iCloud Drive too), the phone remembers its place and reads it again at every opening, so what is changed on the computer is seen on the phone. It is opened with the passphrase; optionally (a switch when opening) the passphrase is kept in the Keychain behind **Face ID** and the vault can be opened with the face (the passphrase is erased when a new face is added to the phone or the passcode is removed). **When the application is locked with Face ID at launch (the Face ID lock), the keys are not locked apart:** after the person gets into the application by the face the vault opens by itself (the passphrase has to be kept behind Face ID; the switch when opening turns on by itself), with no second prompt and no autolock; with the vault closed the key button of the Assistant asks for Face ID at once, with no sheet. What was decrypted lives in memory only and is forgotten: on leaving the application or after a set time in the background (5 minutes by default; at once, 1, 5, 15, 30 minutes or never), on leaving the server and on "Forget server". Viewing: a list with a search and a filter by type, a key shows its login, domain, password (hidden, shown for 10 seconds) and binding; copying a password clears the clipboard after a minute and keeps it off other devices. The keys are made and edited in the desktop application only. The Argon2id (64 MiB, 3 passes) + AES-256-GCM encryption is written anew in Swift and checked against files made by the code of the desktop.
- **Signing in with a key in the Assistant:** on a sign-in, lock or UAC screen a button with a key appears on the panel (an orange dot). It opens the keys of the type UAC and "Any": of this server, of its folder, for all (the rest behind "Show all"). Each key has the main button "Sign in" (login, Tab, password, Enter) and a menu "…" with "Login" (`DOMAIN\login` and Tab) and "Password" (the password and Enter). The window is a compact card in the middle. The text is typed as characters, so the layout and the clipboard do not matter; the audit journal gets the name of the key and the number of characters, no text. "Type by hand…" stays for a text that is not in the keys. A sign-in changes the session of the computer and the connection ends: if that happens within 30 seconds of the sign-in screen or a typing, the Assistant connects again quietly (up to 12 times a minute, 2 seconds apart) and the picture stays.
- A Face ID lock (optional): the screen is covered while the application is in the background.
- Russian and English, a theme of your choice ("Account" → "Appearance": system, light, dark), Dynamic Type and VoiceOver.

## Requirements

An iPhone with iOS 26 or newer (the minimum is 26.0: the glass elements of iOS 26 are needed; it was tried on iOS 27), portrait. A server with the application port (0.10.0-beta.1 or newer). The server has to return `fingerprint_alt` (see below), otherwise the fingerprint cannot be compared by eye.

## First connection and the fingerprint

The server has two certificates with one name (Ed25519 and ECDSA, [connection.md](connection.md)). Apple's TLS gets the ECDSA one, so the fingerprint on the iPhone **does not match** the line `Certificate fingerprint`. Compare it with the line `Fingerprint for iPhone and iPad` of the command:

```bash
sudo linager server app-port
```

If the server prints one line only it is older than this change: update it.

If the fingerprint changes later (the certificate was renewed, or the connection is intercepted) the application does not go on and offers to compare the two fingerprints; the new one is pinned only after a confirmation.

## Build and install

RDP needs the library written in Rust: `brew install rustup`, then `rustup toolchain install stable --profile minimal -t aarch64-apple-ios` (Homebrew does not put `rustup` in the PATH, `ios/build-ipa.sh` finds it by itself). `make ios-ipa` builds `ios/rdp` first (the versions are fixed in `Cargo.lock`), then the application. The tests of `make ios-test` need no Rust; the tests of the library itself: `cargo test --manifest-path ios/rdp/Cargo.toml`.


You need Xcode 27 and XcodeGen (`brew install xcodegen`); on the first build SwiftPM downloads SwiftTerm (the version is pinned in `project.yml`), so the network is needed. SwiftTerm has a build plugin, so the build runs with `-skipPackagePluginValidation` (`make ios-ipa` passes it). No signing and no Apple ID is needed to build:

```bash
make ios-ipa
```

The file `ios/build/Linager.ipa` is built **without a signature**. Your tool (Sideloadly, AltStore, SideStore) signs and installs it with your Apple ID. Limits of a free Apple ID: the signature lasts 7 days (install again after that), up to three applications. Nothing is published to the App Store or to GitHub.

**From a GitHub release.** Every release of the server comes with a ready file `linager-ios_arm64.ipa` (without a signature, like the local build); its checksum is in `SHA256SUMS` and is signed with the other files (minisign). The job `ios-release.yml` builds it on a macOS runner of GitHub: the tests of the logic, the Rust core of RDP, `make ios-ipa`. The version of the application comes from the tag (`v0.10.0-beta.20` gives `0.10.0`), the build number is the number of the run. The build needs Xcode with an SDK no older than the minimum version of the application (iOS 26 now, the runner of GitHub builds with it): the job takes the newest Xcode of the runner and, when the SDK is not there, stops with a plain message. A failure of this job does not stop the rest of the release, the IPA is just not in it (you can always build it yourself and attach it with `gh release upload`). The application does not update itself: a new IPA is downloaded and installed over the old one with the same tool (with a free Apple ID the signature lasts 7 days). The confirmation of devices ([devices.md](devices.md)) shows which phones are connected.

## Structure

| Part | What is in it |
|---|---|
| `ios/Sources/LinagerKit` | Everything but the screens: the certificate pinning (`URLSession` checking the SHA-256 of the leaf certificate before any data is sent), the API client, the event stream, the state of the application, the logic of `status.ts` (levels, thresholds, badges, totals), folders |
| `ios/App` | The SwiftUI screens, the terminal (`TerminalModel`, `TerminalView`: SwiftTerm tied to the `TerminalConnection` channel), the strings (`Localizable.xcstrings`), the icons |
| `ios/project.yml` | The project for XcodeGen (the `.xcodeproj` is not kept) |

App Transport Security is switched off (`NSAllowsArbitraryLoads` in `project.yml`): with it an iPhone broke the TLS connection to the self-signed certificate of the server (error `-1200`, `-9802`) after the application had accepted the fingerprint. The application talks only to the server you name and trusts one certificate there, the pinned one, so the checks of ATS added nothing. Checked on a live phone.

The profile (address, fingerprint, session) lives in the Keychain on this phone only (`WhenUnlockedThisDeviceOnly`). The last dashboard is cached in Caches under file protection and erased on sign-out. The session cookie is kept by hand, not in a shared store.

## Tests

```bash
make ios-test
```

These are the tests of `LinagerKit` on the Mac, without a simulator: parsing of the server answers, thresholds and badges, the folder tree and filters, address parsing, the state of the application on a fake server and **a real TLS connection** to a local server (the fingerprint, a foreign certificate, the sign-in with TOTP, the cookie, CSRF, the event stream, **the terminal over a WebSocket**: data both ways, `resize`, the end of the shell, the limit 4029, an offline agent, a missing right). The screens are not covered by tests: a person checks them on the phone.
