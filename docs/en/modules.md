# Agent modules and configuration

Agent configuration: `/etc/linager/agent.yaml` (created by the installer, permissions 600). Each module can be disabled; after a change run `sudo systemctl restart linager-agent`. A module that is not in the file is enabled. Every time the agent starts it appends the modules the file does not list yet (as `true`) to the `modules:` block and leaves the rest of the file as it is. The application shows tabs only for enabled modules; the tabs of a server are grouped in a sidebar (General, System, File system, Network and security, Applications), and a group with no visible tab is hidden.

```yaml
modules:
  metrics: true      # metrics (always needed by the dashboard)
  terminal: true     # web terminal (root shell)
  services: true     # systemd services
  apt: true          # apt updates
  processes: true    # processes
  logs: true         # journald log
  files: true        # file manager
  disk: true         # disk: partitions, a fill-up forecast, what takes the space, cleanup
  network: true      # network (ifupdown; netplan is view-only)
  firewall: true     # nftables (inet filter table)
  security: true     # security: SSH logins, password guessing, fail2ban, keys
  docker: true       # Docker (enabled only if the socket exists)
```

Reboot (`reboot`) is always available and requires confirmation.

## Module notes
- **apt.** Installing updates is not tied to the browser tab: if you close the tab or the server connection drops, `apt-get` runs to the end. When you come back to the tab, the browser attaches to the running operation and receives all accumulated events and the log. Package statuses come from `APT::Status-Fd` (the `pmstatus`/`pmerror`/`dlstatus` channel), not from the output text: queued → updating → done or error; packages apt never reached after a failure are marked "not updated".
  When the tab is opened again, the installation log is shown from the beginning. If the package database is locked by another process (for example `unattended-upgrades`), the agent waits up to two minutes.
- **security.** The Security tab. It reads data and can change one thing: end remote SSH sessions (the "End" button of a session and "End all sessions" of a user) with `loginctl terminate-session`. The agent ends only sessions from its own fresh list of remote sessions (local console sessions are never touched), the action needs the confirmation of the administrator and is written to the audit log. The processes of the session stop with it (including `tmux` and `screen`). This is not a block: the user can sign in again with a password or a key. systemd-logind is required: sessions it does not track are not shown on the tab. The SSH state from `sshd -T` (from `sshd_config` if that fails): port, root login, password and key login, empty passwords, `AllowUsers`/`AllowGroups`; fail2ban (jails, banned addresses); automatic security updates. For 7 days: successful logins and failed attempts from the systemd journal (`journalctl -t sshd -t sshd-session`; `sshd-session` is needed for OpenSSH 9.8+, which Debian 13 ships), from `/var/log/auth.log` when there is no journal. Failed attempts are counted by address and login, and a login from an address that guessed passwords earlier is flagged. The keys of `authorized_keys` of every user with a shell (the path comes from `AuthorizedKeysFile`): type, RSA size, SHA256 fingerprint, comment, file change time; only fingerprints are sent, the keys never leave the host. Remote sessions from `loginctl`. The answer is cached for a minute and at most 2 million journal lines are read. Only SSH logins are visible (not console or `su`); if the host does not keep the journal across reboots, the history is shorter than 7 days and the tab says so.
- **users.** The "Users" tab (group "Network and security"). It reads `/etc/passwd`, `/etc/group`, `/etc/shadow` (only to tell whether a password is set and whether the account has expired; hashes are never sent anywhere), `/etc/sudoers` and `/etc/sudoers.d`, `loginctl`, `lastlog` (or `lastlog2`) and `/proc`. It shows the regular accounts (UID 1000-59999) and, with a filter, the system ones; root and system accounts are never changed by the panel. Rights: sudo "with a password" is membership in the `sudo` group (`wheel` where there is no `sudo`), "without a password" adds the file `/etc/sudoers.d/linager-<name>` with `NOPASSWD: ALL`, checked with `visudo -c` before it is installed. Groups are chosen only from the ones the agent offers itself (well-known service groups such as `docker`, `adm`, `www-data` and groups made by hand with a GID of 1000 and more); the other groups of a user are left alone. Lock: `usermod -e 1` (the account has expired, so neither a password nor a key works) and `usermod -L`, the sessions are ended with `loginctl terminate-user`. Create: `useradd --create-home --user-group`, the password goes to `chpasswd` on stdin (never into the arguments or the log), the home directory only under `/home`, `/srv`, `/opt`, `/var`, the shell from `/etc/shells`, an SSH key is checked for its shape and written with mode 600. Delete: `loginctl terminate-user` and `pkill -KILL -u` first, then `userdel` (with `--remove` when chosen). The only unlocked user with sudo cannot lose the rights, be locked or deleted while root cannot log in. Every change is confirmed on the server side and written to the audit log. A terminal as a user: the `terminal` stream with a `user` parameter starts `runuser -l <name>`; the agent accepts root and regular accounts with a real shell only. The toolbar of every terminal window has a "User" drop-down that starts the shell again as the chosen account (shown to administrators and to operators who were given the Users module).
- **Ignoring updates (apt and docker).** The "Actions" menu of a package row in the Updates tab and the menu of a Docker container have an "Ignore" item: the package or container stays in the list (its row is dimmed and marked "ignored") but is not counted in the numbers of the dashboard and in the badges of the side menu (Updates and Docker: the number of containers with a newer image). The agent keeps the lists itself (`ignored.json` in its data directory, mode 600, up to 500 entries), so the numbers are counted where the full list is known: ignored packages are left out of `Sample.Updates` and `Sample.SecurityUpdates`, ignored containers out of `Sample.ImageUpdates`. "Install all" installs ignored packages too, "Update marked" skips ignored containers. The commands are `apt.ignore` and `docker.ignore`; the actions go to the audit log (`apt.ignore`, `docker.ignore` and the reverse).
- **disk.** The Disk tab (right after Files). Partitions come from `/proc/mounts` and `statfs`, the same numbers as `df`. For the forecast the agent records the used space of every partition every half hour in `disk-history.json` (the agent data directory, mode 600, 31 days); "fills up in ~N days" is a line through the points of the last two weeks and appears after a day of observation. "What takes the space": on request the agent walks one partition (only one from its own list; symbolic links and other filesystems are not entered, hard links count once, at most 100 seconds, one walk at a time, the result is kept for 10 minutes). Categories: system and packages, Docker, logs, databases, cache and temporary, home directories, other, filesystem reserve, free. "Clean up" offers the journald journal (keep 500 MB), the apt cache, unused Docker images, the Docker build cache and old kernels (the running and the newest one stay). The browser only names the kind of cleanup, the agent works out what to remove; the action needs a confirmation and is audited.
- **fail2ban and keys (security module).** When fail2ban is not installed the tab offers three strictness modes (soft: 10 failures in 10 minutes, a ban for 10 minutes; normal: 5 in 10 minutes for 1 hour; strict: 3 in 10 minutes for 24 hours) and an "Install and enable" button: `apt-get install fail2ban python3-systemd`, the file `/etc/fail2ban/jail.d/linager.conf` (the `[sshd]` jail; never blocked: 127.0.0.0/8, ::1 and the address of the administrator), the `nftables` action when the host has `nft`, then `systemctl enable` and `restart`. The files of the administrator are never rewritten, all settings of the panel live in one file. Afterwards: "Settings" (threshold, ban time, longer bans for repeat offenders, the `recidive` jail, the "Do not block" list, a preview of the file), "Block list" (who is banned now, when the ban ends, the history from `/var/log/fail2ban.log`, "Unban", "Unban selected", "Unban all") and "Block manually" (`fail2ban-client set sshd banip`; 1 hour, 24 hours and 7 days are provided by a transient systemd timer that lifts the ban before the time of the jail). Your own address, loopback and the addresses of the exceptions list cannot be blocked. The failed-attempts table has a "Ban" button for every address. Every action is confirmed on the server and audited. Keys are removed with the "Remove" button: the agent accepts only the `authorized_keys` file it lists itself for that user (a path from the browser selects nothing else), saves a copy `authorized_keys.bak-DATE` before the change and keeps the owner and the mode of the file; the panel warns when it is the last key of the user and password sign-in is off.
- **docker.** Image check: the "Check images" button asks the Docker daemon to compare the digest of the tag in the registry (`/distribution/<image>/json`, with the credentials of the daemon) with the digest of the image on the host; the image is not downloaded. The result is kept in the memory of the agent and shown in the table ("newer image", "up to date", "cannot check"); containers created from an image id or pinned by digest are not checked. "Update marked" updates the containers one after another. Compose containers are grouped by project (collapsed by default): "Update project" (`docker compose pull` and `up -d`), "Restart" or "Start project", "Project logs" (`docker compose logs`). "Update image" in the container menu: the image is pulled again and the container is recreated with the same settings (network, volumes, variables, ports). The old container is stopped and renamed, the new one is started and checked; if it does not start or exits at once, the old one is brought back. A docker compose container is updated with `docker compose pull` and `up -d --no-deps <service>` from the project labels (the `docker` command and the compose plugin are needed on the host). The previous image stays on the host.
- **docker: editing a container.** The "Edit" item in the menu of a container opens a window with the tabs Main (name, image, restart policy, command), Ports, Volumes, Environment and Resources (memory and CPU limits). The agent reads the settings from `inspect` (command `docker.config`; the variables the image sets itself are not shown) and gets the whole wanted state back (stream `docker.edit`), compares it with the current one and decides how to apply it. **In place, without a stop:** the name (`rename`), the restart policy, the memory and CPU limits (`docker update`). **By recreating** (the same as "Update image": the old container is stopped and renamed, the new one is created, started and checked, and if it fails the old one comes back): the image (the new one is pulled), the command, ports, volumes, variables, and taking a limit off. Networks, labels and the rest are carried over as they were; the data in volumes stays, data inside the container outside of volumes is lost. Before applying, the window shows the list of changes and asks for confirmation. The agent checks the names, the image, the ports (including ports taken by another container), absolute volume paths and variable names. A container of a docker compose project may only change the restart policy and the limits: the rest is set by the compose file and would be lost at the next update of the project (the window shows it read-only). The settings go to the server in a request body and the stream carries only a one-time token (valid for 2 minutes), so the values of variables reach neither URLs nor the journal: the audit log (`docker.container.edit`) gets the container, the image, ports, volumes and the **names** of the variables.
- **docker: regular check.** The agent checks the images by itself a minute after start and then every 6 hours (the "Check images" button uses the same code). The number of containers with a newer image is shown on the dashboard as the tag "images: N" (a warning from 5) and in the hint of the updates tile; containers that "cannot be checked" are not counted. The check asks the registry and does not download the image.
- **Firewall: ports and address lists.** The "Ports and connections" block shows what listens (`ss -tulnp`), the number of connections, the process and what the input chain says about the port: allowed by a rule, allowed for some addresses, closed by a rule, no rule (open to everyone with policy accept) or closed by policy drop. Ports published by Docker bypass input and are marked separately. The "Close the port" or "Restrict" button adds a rule to the draft. "Address lists" creates named lists of addresses (nftables `set`s of type ipv4_addr or ipv6_addr with intervals); a rule can use one in the Source field as `@name`. Lists are part of the draft and are applied with the rules, with a rollback in 30 seconds; a list that rules use cannot be deleted. The input, forward and output chains are shown as tabs.
- **DNS on the Network tab.** The "Edit" button of the DNS card: 1-3 name servers and up to 6 search domains. The agent picks where to write by itself: systemd-resolved (`/etc/systemd/resolved.conf.d/linager.conf`), resolvconf (the `dns-*` lines of the primary interface) or a plain `/etc/resolv.conf`; on netplan hosts DNS is view-only. The change uses the same confirm window with a rollback after 30 seconds as editing interfaces and is audited (`network.dns`). The primary interface is always first and open, the others are folded into one line.
- **Firewall: journal.** The "Journal" button opens a window with the matches of the rules. The firewall writes nothing by itself: a rule has a "Journal" switch that adds `limit rate 5/second log prefix "lg:<chain>:<id>:<A|D|R> "` to it (the id is short and comes from the text of the rule; A, D and R mean accept, drop and reject). The kernel writes such packets to its journal, the agent reads it (`journalctl -k`, 7 days, only the lines with the `lg:` mark, at most 6000 newest events, the answer is cached for 15 seconds) and gives the panel the time, the chain, the rule, the action, the interface, the source, the destination, the protocol, the ports, the size and the TCP flags. The window has a period (15 minutes, 1 hour, 24 hours, 7 days), a histogram, filters by chain, action and protocol in any combination, by port (`22`, `80, 443`, `1000-2000`) and by source (an address, the start of a network or `@list`), grouping of identical events, an expandable row, a CSV export, and from a row: add the source to an address list, block the address (a rule first in input) or open the rule. Every change goes to the draft. While no rule is marked, the window explains how to switch the record on. `journalctl` is required.
- **Terminal.** Snippets (commands shared by all users) are managed in Settings → Snippets; in the terminal the Snippets list pastes a command and runs it, while the button at the right of the row only pastes it.
- **assistant (Linux).** The "Assistant" tab for a Linux computer with a graphical console: the screen of the desktop and its control in the application (mouse, keyboard, text clipboard, a choice of the monitor), with no new session and no question to the person at the computer. It needs **GNOME on Wayland** (Ubuntu 26.04 has no other session) and the packages `gstreamer1.0-tools` and `gstreamer1.0-pipewire` (usually installed on Ubuntu Desktop); somebody must be signed in to the desktop on the screen. How it works: the agent (root) finds the active graphical session of the console in logind and starts a helper as the person of that session (`linager agent assistant-helper`, the same file); the helper asks GNOME Mutter over D-Bus for the stream of a monitor (`org.gnome.Mutter.ScreenCast`) and a remote-desktop session (`RemoteDesktop`) without a dialog, reads the frames with `gst-launch-1.0 pipewiresrc` (raw BGRA frames through a pipe), the mouse and the keys go to Mutter (evdev codes; the scan codes of the browser are translated), the text clipboard through the `Selection*` methods. The picture is encoded with the same JPEG tiles and the same quality settings as on Windows. The agent says in its sample that the computer has a graphical console (the field `gui`), and the panel shows the tab, the buttons and the menu items only for such computers; Ctrl+Alt+Del, the Windows task manager and "Management" are not shown for Linux. **The sign-in screen, the lock screen and X11 sessions** are not shown to a screen cast by GNOME (gnome-shell inhibits remote access in those modes), so they are read **below the compositor**: the helper runs as root, reads the frame the graphics card puts on the screen (DRM/KMS: `/dev/dri/card*`, `GETFB2`, dma-buf) and makes the mouse and the keys as a kernel device (`/dev/uinput`); the panel marks this screen with the badge of the lock or sign-in screen. Limits of this mode: only a linear (not tiled) frame is read, which is virtual machines and some graphics cards; Intel and AMD with a tiled buffer need the GPU, and the helper says so; there is no text clipboard; the pointer of the computer is in the picture only where the computer draws it itself (on the sign-in screen of a virtual machine it often does), and the setting "show the pointer" does not act on it (on the desktop it does); the displays are picked by controllers. **It switches by itself:** when the person signs out of the desktop or locks the screen, GNOME closes the screen cast; the helper asks the browser to connect again, and the sign-in or lock screen replaces the desktop without service messages (the last picture stays, and the notice of a lost connection appears only when the reconnection fails); after the sign-in or the unlock the desktop comes back the same way. **A dark screen.** If the monitor went dark (the sign-in or the lock screen turns it off by itself), the Assistant wakes it with a press of Shift on a virtual keyboard (it does nothing on those screens) and shows the plain "Connecting to the session…" stub, with a note that the screen is being switched on, until the first picture comes; if the screen does not light up in 10 seconds (the monitor is switched off, the computer is asleep) the session ends with the reason. The same happens when the screen goes dark while the Assistant is open. The browser reconnects not more than four times in 40 seconds. Not yet: KDE, wlroots, the item "All monitors", a native PipeWire client (GStreamer reads the frames, which costs processor time and needs the packages). Drawing the pointer of the computer into the picture and choosing another monitor open the session again, the input stops for a moment. The helper writes to the log of the agent (`journalctl -u linager-agent`), the reasons of a failure are there.
- **The "Files" and "Dispatcher" buttons.** The bar of every connection (terminal, remote desktop, Assistant; in a tab, a floating window and the Console) has two icon buttons: "Files" opens the "Files" tab in a floating window (the same as the item of the context menu of the Console), "Dispatcher" opens the window of the processes and the services (see "Assistant" in windows.md). A button is there for whoever has the right for the module (files; processes or services). The Dispatcher works on Linux too: "End" sends SIGTERM, "Force end" SIGKILL, the services go through systemd.
- **Network and firewall.** An unconfirmed change is rolled back by the agent itself after 30 seconds. In case the agent process has crashed or hangs there is a second line of defence:
  a one-shot systemd timer (`linager-agent-change-rollback`) runs the rollback in a separate process after 35 seconds.
- **Firewall.** The "rules close SSH" warning uses the ports sshd really listens on (`sshd -T`), not only port 22.
- **The agent certificate** is issued for one year and renews itself: when less than a third of the lifetime is left, the agent asks for a new one over the protected channel.
  If a host was switched off for longer than the certificate lifetime, enroll it again (`linager install`).
  The lifetime is set on the server: `agents.cert_lifetime` in `server.yaml` (for example `2160h`, default `8760h`).

## The note of a server
On the server page, left of the "Reboot" button, there is a button with a note icon (a small square in its corner shows that the note exists). It opens the "Note" window: free text of up to 20,000 characters, for example who owns the server, what it is for, where its backups are. Everyone who can see the server reads the note; an administrator changes it: the pencil next to the cross starts editing, "Cancel" and "Save" return to the text without closing the window (`Ctrl+Enter` saves, `Esc` in the editor cancels the edit). Markdown is supported: headings, **bold**, *italic*, ~~strike~~, `code` and code blocks, lists (nested, and tasks `- [ ]`), quotes, links (`http`, `https` and `mailto` only), a horizontal rule. The text is escaped before the markup is added, so HTML in a note is never run. The audit journal records that the note changed and its length (`server.note`), not the text. API: the note comes with `GET /api/servers/{id}` (`note`, `note_updated_at`, `note_updated_by`) and is saved with `PUT /api/servers/{id}/note`.

## Agent files and directories
| Path | Purpose |
|---|---|
| `/usr/local/bin/linager` | binary (server and agent) |
| `/etc/linager/agent.yaml` | enabled modules |
| `/var/lib/linager-agent/` | key, certificate, state, rollback journal (`pending.json`), `linager.prev` |
| `/etc/systemd/system/linager-agent.service` | agent service |

## Client commands
```bash
linager agent status          # version, server, state
sudo linager agent update     # update from the server
sudo linager agent uninstall --purge   # remove from the host (keys and config)
```

## Removing a client from the application
Server card, "Delete server": enter the server name and select "Also remove the agent from the server itself" (if the server is online, the agent deletes its keys and service and stops). The record and its history are deleted, and the agent certificate stops working immediately.
