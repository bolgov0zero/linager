# Модули агента и конфигурация

Конфигурация агента: `/etc/linager/agent.yaml` (создаётся установщиком, права 600). Каждый модуль можно отключить; после изменения: `sudo systemctl restart linager-agent`. Модуль, которого нет в файле, включён. При каждом запуске агент дописывает в блок `modules:` модули, которых в файле ещё нет (со значением `true`), остальное содержимое файла не трогает. Админка показывает вкладки только включённых модулей; вкладки сервера собраны в боковом меню по группам (Общее, Система, Файловая система, Сеть и защита, Приложения), группа без видимых вкладок скрыта.

```yaml
modules:
  metrics: true      # метрики (всегда нужны дашборду)
  terminal: true     # веб-терминал (оболочка root)
  services: true     # службы systemd
  apt: true          # обновления apt
  processes: true    # процессы
  logs: true         # журнал journald
  files: true        # файловый менеджер
  disk: true         # диск: разделы, прогноз заполнения, что занимает место, очистка
  network: true      # сеть (ifupdown; netplan только просмотр)
  firewall: true     # nftables (таблица inet filter)
  security: true     # безопасность: входы по SSH, подбор паролей, fail2ban, ключи
  docker: true       # Docker (включается, только если есть сокет)
```

Перезагрузка (`reboot`) доступна всегда и требует подтверждения.

## Особенности модулей
- **apt.** Установка обновлений не привязана к вкладке приложения: если закрыть вкладку или связь с сервером оборвётся, `apt-get` доработает до конца. Вернувшись на вкладку, приложение подключается к идущей операции и получает все накопленные события и лог. Статусы пакетов агент берёт из `APT::Status-Fd` (канал `pmstatus`/`pmerror`/`dlstatus`), а не из текста вывода: пакет в очереди → обновление → завершено или ошибка; пакеты, до которых apt не дошёл после сбоя, получают «не обновлён».
  При повторном открытии журнал установки показывается с начала. Если пакетная база занята другим процессом (например, `unattended-upgrades`), агент ждёт до двух минут.
- **security.** Вкладка «Безопасность». Читает данные, а менять умеет: завершать удалённые SSH-сессии, управлять fail2ban и удалять ключи из `authorized_keys`. Завершать удалённые SSH-сессии (кнопка «Завершить» у сессии и «Завершить все сессии» пользователя) командой `loginctl terminate-session`. Агент завершает только сессии из собственного свежего списка удалённых сессий (локальные консольные не трогает), действие требует подтверждения администратора и пишется в журнал аудита. Процессы сессии останавливаются вместе с ней (в том числе `tmux` и `screen`). Это не блокировка: пользователь войдёт снова по паролю или ключу. Нужен systemd-logind: сессии, которых он не ведёт, на вкладке не видны. Установка, настройка и блокировки fail2ban (см. ниже). Состояние SSH из `sshd -T` (при ошибке из `sshd_config`): порт, вход root, вход по паролю и по ключу, пустые пароли, `AllowUsers`/`AllowGroups`; fail2ban (правила, забаненные адреса); автообновления безопасности. За 7 дней: успешные входы и неудачные попытки из журнала systemd (`journalctl -t sshd -t sshd-session`; `sshd-session` нужен для OpenSSH 9.8+, в нём Debian 13), при отсутствии журнала из `/var/log/auth.log`. Неудачные попытки считаются по адресам и логинам, вход с адреса, который до этого подбирал пароль, помечается. Ключи из `authorized_keys` каждого пользователя с оболочкой (путь берётся из `AuthorizedKeysFile`): тип, размер RSA, отпечаток SHA256, комментарий, дата изменения файла; передаются только отпечатки, сами ключи не покидают хост. Удалённые сессии из `loginctl`. Ответ кэшируется на минуту, читается не больше 2 млн строк журнала. Видны только входы по SSH (консольные и `su` нет); если журнал на хосте не сохраняется после перезагрузки, история будет короче 7 дней, вкладка об этом предупредит.
- **users.** Вкладка «Пользователи» (группа «Сеть и защита»). Читает `/etc/passwd`, `/etc/group`, `/etc/shadow` (только чтобы узнать, задан ли пароль и истёк ли срок учётной записи, хэши никуда не передаются), `/etc/sudoers` и `/etc/sudoers.d`, `loginctl`, `lastlog` (или `lastlog2`) и `/proc`. Показывает обычные учётные записи (UID 1000–59999) и по фильтру системные; root и системные записи панель не меняет. Права: sudo «с паролем» — членство в группе `sudo` (на системах без неё `wheel`), «без пароля» — ещё и файл `/etc/sudoers.d/linager-<имя>` со строкой `NOPASSWD: ALL`, который перед установкой проверяет `visudo -c`. Группы выбираются только из тех, что агент предлагает сам (известные служебные вроде `docker`, `adm`, `www-data` и созданные вручную с GID от 1000); остальные группы пользователя не трогаются. Блокировка: `usermod -e 1` (срок учётной записи истёк, не работают ни пароль, ни ключ) и `usermod -L`, сеансы завершаются `loginctl terminate-user`. Создание: `useradd --create-home --user-group`, пароль через `chpasswd` на stdin (в аргументы и журнал не попадает), домашний каталог только в `/home`, `/srv`, `/opt`, `/var`, оболочка из `/etc/shells`, ключ SSH проверяется по форме и записывается с правами 600. Удаление: сначала `loginctl terminate-user` и `pkill -KILL -u`, затем `userdel` (с `--remove`, если выбрано). Единственного разблокированного пользователя с sudo нельзя лишить прав, заблокировать или удалить, пока вход под root закрыт. Все изменения подтверждаются на стороне сервера и пишутся в журнал аудита. Терминал от имени пользователя: поток `terminal` с параметром `user` запускает `runuser -l <имя>`; агент принимает только root и обычные записи с настоящей оболочкой. В приложении инструментов любого окна терминала есть выпадающий список «Пользователь»: он перезапускает оболочку от имени выбранной записи (виден администратору и оператору с модулем «Пользователи»).
- **Игнорирование обновлений (apt и docker).** В меню «Действия» строки пакета на вкладке «Обновления» и в меню контейнера Docker есть пункт «Игнорировать»: пакет или контейнер остаётся в списке (строка тусклая, с пометкой «игнорируется»), но не считается в числах дашборда и в бейджах боковой панели (у «Обновлений» и у «Docker»: число контейнеров с новым образом). Списки ведёт сам агент (файл `ignored.json` в его каталоге данных, права 600, до 500 записей), поэтому числа считаются там, где известен полный список: игнорируемые пакеты не входят в `Sample.Updates` и `Sample.SecurityUpdates`, игнорируемые контейнеры в `Sample.ImageUpdates`. «Установить все» ставит и игнорируемые пакеты, «Обновить помеченные» пропускает игнорируемые контейнеры. Команды `apt.ignore` и `docker.ignore`, действия пишутся в аудит (`apt.ignore`, `docker.ignore` и обратные).
- **disk.** Вкладка «Диск» (после «Файлов»). Разделы берутся из `/proc/mounts` и `statfs`, как в `df`. Для прогноза агент сам раз в полчаса записывает занятое место каждого раздела в `disk-history.json` (каталог данных агента, права 600, 31 день); прогноз «заполнится через ~N дней» строится по прямой через точки последних двух недель и появляется после суток наблюдения. «Что занимает место»: по кнопке агент обходит один раздел (только тот, что есть в его списке, символические ссылки и другие файловые системы не заходятся, жёсткие ссылки считаются один раз, не дольше 100 секунд, за раз один обход, результат хранится 10 минут). Категории: система и пакеты, Docker, журналы, базы, кэш и временные, домашние каталоги, прочее, резерв ФС, свободно. «Очистка» предлагает журнал journald (оставить 500 МБ), кэш apt, неиспользуемые образы Docker, кэш сборки Docker и старые ядра (остаются запущенное и самое новое). Браузер называет только вид очистки, а что именно удалять, агент определяет сам; действие требует подтверждения и пишется в аудит.
- **fail2ban и ключи (модуль security).** Если fail2ban не установлен, вкладка предлагает три режима строгости (мягко: 10 неудач за 10 минут, бан на 10 минут; обычно: 5 за 10 минут на 1 час; строго: 3 за 10 минут на 24 часа) и кнопку «Установить и включить»: `apt-get install fail2ban python3-systemd`, файл `/etc/fail2ban/jail.d/linager.conf` (правило `[sshd]`, исключения из блокировки: 127.0.0.0/8, ::1 и адрес администратора), действие `nftables`, если на хосте есть `nft`, затем `systemctl enable` и `restart`. Файлы администратора агент не переписывает, вся настройка панели лежит в одном файле. После установки: «Настройки» (порог, срок бана, увеличение срока для повторных нарушителей, правило `recidive`, список «Не блокировать», просмотр файла), «Список блокировок» (кто забанен сейчас, когда разбан, история из `/var/log/fail2ban.log`, «Разбанить», «Разбанить выбранные», «Разбанить все») и «Заблокировать вручную» (`fail2ban-client set sshd banip`; сроки 1 час, 24 часа и 7 дней обеспечивает одноразовый таймер systemd, который снимает бан раньше срока правила). Свой адрес, loopback и адреса из списка исключений заблокировать нельзя. В таблице неудачных попыток у адресов есть кнопка «Забанить». Все действия подтверждаются на стороне сервера и пишутся в аудит. Ключи для входа удаляются кнопкой «Удалить»: агент принимает только тот файл `authorized_keys`, который сам показывает для этого пользователя (путь из браузера ничего другого не выбирает), перед удалением сохраняет копию `authorized_keys.bak-ДАТА`, оставляет владельца и права файла; панель предупреждает, если это последний ключ пользователя, а вход по паролю отключён.
- **docker.** Проверка образов: кнопка «Проверить образы» просит демон Docker сравнить digest тега в реестре (`/distribution/<образ>/json`, с учётными данными демона) с digest образа на хосте; образ не скачивается. Результат хранится в памяти агента и показывается в таблице («есть новый», «актуален», «нельзя проверить»); контейнеры, созданные из id образа или закреплённые по digest, не проверяются. «Обновить помеченные» обновляет контейнеры по очереди. Контейнеры compose сгруппированы по проектам (свёрнуты по умолчанию): «Обновить проект» (`docker compose pull` и `up -d`), «Перезапустить» или «Запустить проект», «Логи проекта» (`docker compose logs`). «Обновить образ» в меню контейнера: образ загружается заново, контейнер пересоздаётся с теми же настройками (сеть, тома, переменные, порты). Старый контейнер останавливается и переименовывается, новый запускается и проверяется; если он не стартовал или сразу вышел, возвращается старый. Контейнер из docker compose обновляется командами `docker compose pull` и `up -d --no-deps <сервис>` по меткам проекта (нужны команда `docker` и плагин compose на хосте). Прежний образ остаётся на хосте.
- **docker: изменение контейнера.** Пункт «Изменить» в меню контейнера открывает окно с вкладками «Основное» (имя, образ, политика перезапуска, команда запуска), «Порты», «Тома», «Окружение» и «Ресурсы» (лимиты памяти и CPU). Агент читает настройки из `inspect` (команда `docker.config`; переменные, которые задаёт сам образ, не показываются) и получает назад всё желаемое состояние (поток `docker.edit`), сам сравнивает его с текущим и решает, как применить. **На месте, без остановки:** имя (`rename`), политика перезапуска, лимиты памяти и CPU (`docker update`). **С пересозданием** (то же, что «Обновить образ»: старый контейнер останавливается и переименовывается, новый создаётся, запускается и проверяется, при неудаче возвращается старый): образ (новый скачивается), команда, порты, тома, переменные, а также снятие лимита. Сети, метки и прочее переносятся как были; данные в томах сохраняются, данные внутри самого контейнера вне томов пропадают. Перед применением окно показывает список изменений и просит подтверждения. Проверки на агенте: имена, образ, порты (в том числе занятые другим контейнером), абсолютные пути томов, имена переменных. Контейнер из docker compose меняет только политику перезапуска и лимиты: остальное задаёт compose-файл и пропало бы при следующем обновлении проекта (в окне это только для чтения). Настройки уходят на сервер телом запроса, а в поток передаётся только одноразовый токен (действует 2 минуты), поэтому значения переменных не попадают ни в адреса, ни в журнал: в аудит (`docker.container.edit`) пишутся контейнер, образ, порты, тома и **имена** переменных.
- **docker: регулярная проверка.** Агент сам проверяет образы через минуту после старта и затем раз в 6 часов (кнопка «Проверить образы» использует тот же код). Число контейнеров с новым образом показывается на дашборде тегом «образы: N» (предупреждение от 5) и в подсказке плитки обновлений; контейнеры «нельзя проверить» в число не входят. Проверка идёт через реестр без скачивания образа.
- **Терминал.** Сниппеты (команды, общие для всех пользователей) настраиваются в «Настройки → Сниппеты»; в терминале список «Сниппеты» вставляет команду и выполняет её, а кнопка справа от пункта только вставляет.
- **assistant (Linux).** Вкладка «Помощник» для Linux-компьютера с графической консолью: экран рабочего стола и управление им в приложении (мышь, клавиатура, текстовый буфер, выбор монитора), без новых сеансов и без запроса у человека за компьютером. Нужны **GNOME на Wayland** (в Ubuntu 26.04 другого сеанса нет) и пакеты `gstreamer1.0-tools` с `gstreamer1.0-pipewire` (на Ubuntu Desktop обычно уже стоят); на экране должен быть выполнен вход в рабочий стол. Как это работает: агент (root) находит активный графический сеанс консоли в logind и запускает от имени этого пользователя помощника (`linager agent assistant-helper`, тот же файл); помощник по D-Bus просит у GNOME Mutter поток монитора (`org.gnome.Mutter.ScreenCast`) и сеанс удалённого управления (`RemoteDesktop`) без диалога, кадры читает `gst-launch-1.0 pipewiresrc` (сырые кадры BGRA через канал), мышь и клавиши идут в Mutter (коды evdev, сканкоды из браузера переводятся), текстовый буфер через методы `Selection*`. Картинка кодируется теми же плитками JPEG и теми же настройками качества, что и в Windows. Агент сообщает в замере, что у машины есть графическая консоль (поле `gui`), и панель показывает вкладку, кнопки и пункты меню только таким машинам; Ctrl+Alt+Del, диспетчер задач Windows и «Управление» для Linux не показываются. **Экран входа, экран блокировки и сеансы X11** GNOME не показывает захвату экрана (gnome-shell запрещает удалённый доступ в этих режимах), поэтому их читают **ниже компоситора**: помощник запускается от root, читает кадр, который видеокарта выводит на экран (DRM/KMS: `/dev/dri/card*`, `GETFB2`, dma-buf), а мышь и клавиши создаёт как устройство ядра (`/dev/uinput`); в приложении этот экран помечен значком экрана блокировки или входа. Ограничения этого режима: читается только линейный (нетайловый) кадр, а это виртуальные машины и часть видеокарт, на Intel и AMD с тайловым буфером нужен GPU, и помощник скажет об этом; нет текстового буфера; указатель компьютера виден в картинке только там, где его рисует сам компьютер (на экране входа в виртуальной машине часто так), и настройка «показывать курсор» на него не действует (на рабочем столе она работает); мониторы выбираются по контроллерам. **Переключение само:** когда человек выходит из рабочего стола или блокирует экран, GNOME закрывает сеанс захвата; помощник просит приложение подключиться снова, и экран входа или блокировки сменяет рабочий стол без служебных сообщений (последняя картинка остаётся на месте, уведомление о разрыве появляется, только если переподключиться не удалось); после входа или разблокировки так же возвращается рабочий стол. **Погасший экран.** Если монитор погас (экран входа или блокировки гаснет сам), помощник будит его нажатием Shift через виртуальную клавиатуру (на экране входа и блокировки оно ничего не делает), а до первой картинки показывает обычную заглушку «Подключение к сеансу…» с пояснением, что экран включается; если за 10 секунд экран не включился (монитор выключен кнопкой, компьютер спит), сеанс закрывается с причиной. То же происходит, если экран погас уже во время сеанса. Браузер переподключается не больше четырёх раз за 40 секунд. Пока нет: KDE, wlroots, пункт «Все мониторы», нативный клиент PipeWire (кадры читает GStreamer, это нагрузка на процессор и зависимость от пакетов). Показ курсора компьютера в кадре и выбор другого монитора перезапускают сеанс, ввод на мгновение прерывается. Помощник пишет в журнал агента (`journalctl -u linager-agent`), там видны причины отказов.
- **Кнопки «Файлы» и «Диспетчер».** На панели любого подключения (терминал, удалённый рабочий стол, Помощник; во вкладке, плавающем окне и Консоли) есть две кнопки-иконки: «Файлы» открывает вкладку «Файлы» в плавающем окне (то же, что пункт контекстного меню Консоли), «Диспетчер» открывает окно процессов и служб (см. «Помощник» в windows.md). Кнопка есть у тех, у кого есть права на модуль (файлы; процессы или службы). Диспетчер работает и на Linux: «Завершить» посылает SIGTERM, «Принудительно завершить» SIGKILL, службы идут через systemd.
- **Сеть и файрвол.** Неподтверждённую правку через 30 секунд откатывает сам агент. На случай, если процесс агента упал или завис, есть второй рубеж:
  одноразовый таймер systemd (`linager-agent-change-rollback`) через 35 секунд запускает откат отдельным процессом.
- **Файрвол: порты и адресные листы.** Блок «Порты и соединения» показывает, какие порты слушаются (`ss -tulnp`), число соединений, процесс и что про порт говорит цепочка input: разрешён правилом, разрешён части адресов, закрыт правилом, нет правила (открыт всем при политике accept) или закрыт политикой drop. Порты, которые публикует Docker, идут мимо input и помечены отдельно. Кнопка «Закрыть порт» или «Ограничить» добавляет правило в черновик. «Адресные листы» создают именованные списки адресов (множества nftables `set`, типы ipv4_addr и ipv6_addr с интервалами), в правилах их можно указать в поле «Источник» как `@имя`. Списки входят в черновик и применяются вместе с правилами, с откатом через 30 секунд; список, который используется в правилах, удалить нельзя. Цепочки input, forward и output переключаются вкладками.
- **DNS на вкладке «Сеть».** Кнопка «Изменить» в карточке DNS: 1–3 сервера имён и до 6 доменов поиска. Агент сам выбирает, куда писать: systemd-resolved (файл `/etc/systemd/resolved.conf.d/linager.conf`), resolvconf (строки `dns-*` основного интерфейса) или обычный `/etc/resolv.conf`; на хостах с netplan DNS только для просмотра. Изменение идёт через то же окно подтверждения с откатом через 30 секунд, что и правка интерфейсов, и пишется в аудит (`network.dns`). Основной интерфейс всегда первый и раскрыт, остальные свёрнуты в строку.
- **Файрвол: журнал.** Кнопка «Журнал» открывает окно со срабатываниями правил. Файрвол сам ничего не пишет: у правила есть переключатель «Журнал», он добавляет к правилу `limit rate 5/second log prefix "lg:<цепочка>:<id>:<A|D|R> "` (id короткий, считается из текста правила, A, D и R значат accept, drop и reject). Ядро пишет такие пакеты в свой журнал, агент читает его (`journalctl -k`, за 7 дней, только строки с меткой `lg:`, до 6000 новейших событий, ответ кэшируется на 15 секунд) и отдаёт панели: время, цепочку, правило, действие, интерфейс, источник, получатель, протокол, порты, размер и флаги TCP. Окно умеет период (15 минут, 1 час, 24 часа, 7 дней), гистограмму, фильтры по цепочке, действию и протоколу в любой комбинации, порту (`22`, `80, 443`, `1000-2000`) и источнику (адрес, начало сети или `@список`), объединение одинаковых событий, раскрытие строки, экспорт в CSV, а из строки: добавить источник в адресный лист, заблокировать адрес (правило первым в input) или открыть правило. Все изменения идут в черновик. Пока ни одно правило не помечено, окно объясняет, как включить запись. Нужен `journalctl`.
- **Файрвол.** Предупреждение «правила закрывают SSH» строится по портам, на которых sshd слушает на самом деле (`sshd -T`), а не только по порту 22.
- **Сертификат агента** выдаётся на год и продлевается сам: когда остаётся меньше трети срока, агент запрашивает новый по защищённому каналу.
  Если хост был выключен дольше срока действия сертификата, его нужно привязать заново (`linager install`).
  Срок задаётся на сервере: `agents.cert_lifetime` в `server.yaml` (например `2160h`, по умолчанию `8760h`).

## Заметка к серверу
На странице сервера слева от кнопки «Перезагрузить» есть кнопка с иконкой заметки (в углу появляется квадрат, когда заметка есть). Она открывает окно «Заметка»: произвольный текст до 20 000 символов, например владелец сервера, назначение, где лежат бэкапы. Заметку видят все, кто видит сервер; менять её может администратор: карандаш рядом с крестиком открывает редактирование, «Отмена» и «Сохранить» возвращают к тексту, не закрывая окно (`Ctrl+Enter` сохраняет, `Esc` в редакторе отменяет правку). Поддерживается Markdown: заголовки, **жирный**, *курсив*, ~~зачёркнутый~~, `код` и блоки кода, списки (с вложением и задачами `- [ ]`), цитаты, ссылки (только `http`, `https`, `mailto`), горизонтальная черта. Текст экранируется до разметки, HTML в заметке не выполняется. В журнал аудита пишется факт изменения и длина текста (`server.note`), не сам текст. API: заметка приходит в `GET /api/servers/{id}` (`note`, `note_updated_at`, `note_updated_by`), сохраняется `PUT /api/servers/{id}/note`.

## Файлы и каталоги агента
| Путь | Назначение |
|---|---|
| `/usr/local/bin/linager` | бинарник (сервер и агент) |
| `/etc/linager/agent.yaml` | включённые модули |
| `/var/lib/linager-agent/` | ключ, сертификат, состояние, журнал отката (`pending.json`), `linager.prev` |
| `/etc/systemd/system/linager-agent.service` | служба агента |

## Команды клиента
```bash
linager agent status          # версия, сервер, состояние
sudo linager agent update     # обновить с сервера
sudo linager agent uninstall --purge   # удалить с хоста (ключи и конфиг)
```

## Удаление клиента из приложения
Карточка сервера, «Удалить сервер»: введите имя сервера, отметьте «Также удалить агента с самого сервера» (если он онлайн, агент удалит свои ключи и службу и остановится). Запись и история удаляются, сертификат агента перестаёт работать сразу.
