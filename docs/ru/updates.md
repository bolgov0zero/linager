# Обновления, резервные копии и откат

## Как устроены релизы
Каждый релиз на GitHub содержит бинарники `linager_linux_amd64` и `linager_linux_arm64`, файлы Windows-агента (`linager-agent_windows_amd64.exe` и `.msi`), приложение (`linager-desktop_…`), `SHA256SUMS` и подписанный `manifest.json` (версия, канал, контрольные суммы бинарников по архитектурам, число миграций БД, минимальная версия агента, список изменений). Подпись minisign (Ed25519) проверяется открытым ключом, **вшитым в бинарник**. Бинарник, не совпавший с подписанным манифестом, не устанавливается ни на сервере, ни на агенте.

## Обновление сервера
Из приложения: страница «Обновления» (кнопка в шапке со счётчиком), «Обновить до X». С терминала:

```bash
sudo linager update --check      # что доступно
sudo linager update              # обновить (спросит подтверждение, --yes чтобы не спрашивать)
```

Порядок (виден в приложении по шагам): проверка подписи → резервная копия (`pg_dump` + конфигурация и ключи) → остановка службы → замена бинарника (предыдущий хранится в `/var/lib/linager-updater/prev/`, каталог доступен только root) → миграции БД (только вперёд) → запуск и проверка (админка отвечает 200, порт клиентов принимает соединения, до 60 с). **Если проверка не прошла, предыдущий бинарник возвращается автоматически.** Миграции откатить нельзя, поэтому перед каждым обновлением делается копия БД: `/var/backups/linager/linager-pre-update-*.tar.gz`. Если сбой случился уже после миграций, вместе с бинарником из этой копии **автоматически восстанавливается база**: прежняя версия не должна работать на новой схеме. Если восстановить базу не удалось, в сообщении об ошибке будет готовая команда `linager restore …`.

Проверенный бинарник перед остановкой службы копируется в каталог, доступный только root (`/var/lib/linager-updater/`), и перед установкой его контрольная сумма сверяется ещё раз: кэш релизов доступен на запись службе сервера и после проверки ему больше не доверяют. **Понижение версии запрещено**: подписанный, но более старый релиз не установится ни из приложения, ни командой `linager update`. Если понижение действительно нужно: `sudo linager update --version vX.Y.Z --allow-downgrade` (база при этом назад не мигрирует).

Из приложения обновление запускает служба `linager-updater` (systemd path-юнит следит за файлом запроса и запускает `linager update --apply-request` от root): сама служба сервера работает без прав root и заменить бинарник не может. Установщик создаёт эти юниты.

## Обновление агентов
Агенты берут релиз **с сервера** (порт клиентов, mTLS), поэтому сначала обновляется сервер. На странице «Обновления» можно обновить одного, выбранных или всех; порядок: все сразу, по одному, сначала один и потом остальные; опция «остановить при ошибке». Офлайн-агент встаёт в очередь и обновляется при подключении. Раскатка переживает перезапуск сервера: очередь продолжается с того же места. В режиме «сначала один» сбой первого агента останавливает раскатку, если включено «остановить при ошибке»; иначе остальные обновляются дальше. Агент отказывается ставить версию старше своей. Агент старше минимальной поддерживаемой версии помечается «не поддерживается».

Агент проверяет подпись и контрольную сумму, сохраняет прежний бинарник (`/var/lib/linager-agent/linager.prev`), заменяет `/usr/local/bin/linager`, запускает **таймер отката** (`systemd-run`, исполняет прежний бинарник) и перезапускается. Новая версия подтверждает себя первым успешным подключением к серверу и отменяет таймер. **Если подключения нет, через ~70 с прежний бинарник возвращается автоматически.** Вручную на хосте клиента: `sudo linager agent update`, `linager agent status`.

### Этапы обновления агента
Ход обновления виден списком этапов: на странице сервера (в рамке под шапкой) и на странице «Обновления» в строке агента (кнопка «Этапы»). У каждого этапа есть отметка, время и подробности:

| Этап | Что показывает |
|---|---|
| Загрузка | объём (`7,2 МБ из 18,4 МБ`) |
| Проверка подписи и хеша | |
| Резервная копия | |
| Замена файла, таймер отката | с этого момента идёт отсчёт отката |
| Перезапуск службы | |
| Агент офлайн | сколько секунд агента нет и сколько осталось до отката |
| Новая версия подключилась | версия, с которой агент вернулся |
| Подтверждение | новая версия сняла таймер отката |

Первые пять этапов сообщает сам агент, последние три видит сервер: обрыв соединения, приветствие новой версии и событие «подтверждено». Поэтому перезапуск не выглядит «чёрным ящиком». Если агент вернулся со старой версией, отмечается этап «подключилась» как неудавшийся, а при ошибке на любом этапе видно, где и почему остановилось (текст ошибки под этапом). Список хранится только для текущего запуска: после успеха он исчезает, после ошибки или отката остаётся до следующего запуска. Агент старее этой версии не сообщает начало и конец этапов: для него список строится по его событиям, а три последних этапа видны полностью.

### Лимит времени и журнал обновления
На всё обновление (загрузка релиза, проверка, резервная копия, замена) агенту отведено **10 минут**, остальные команды ограничены двумя. Сервер ждёт ответа на 2 минуты дольше. Если загрузка не укладывается, этап «Загрузка» заканчивается ошибкой `context deadline exceeded` с временем, за которое она оборвалась.

Для разбора неудачного обновления:
- **Журнал агента** (`journalctl -u linager-agent`) пишет строки `update: …` по каждому этапу: начало с версиями и архитектурой, ответ сервера на запрос бинарника и время ожидания, раз в 10 секунд ход загрузки (байты, процент, средняя скорость и скорость за интервал, `idle_s` показывает, сколько секунд не приходило ни одного байта), конец этапа и его длительность, а при ошибке этап, причину и `timed_out=true`, если вышло время. Последняя строка успешного обновления: `update: installed, the rollback timer is armed`, после перезапуска `update confirmed`.
- **Журнал сервера** (`journalctl -u linager`) пишет `agent update: …`: команду и ожидание, этапы, которые сообщил агент, обрыв соединения во время обновления (с номером этапа и временем с последнего сообщения), возвращение агента на новой или старой версии, подтверждение, ошибку или откат. Строки `release file: sent` показывают, сколько байт реально отдано агенту, за сколько миллисекунд и с какой скоростью, а `release file: the transfer did not finish` говорит о том, что агент оборвал загрузку.

## Каналы и источник релизов
Канал `stable` (теги `vX.Y.Z`) или `beta` (`vX.Y.Z-beta.N`) выбирается в приложении. В `/etc/linager/server.yaml`:

```yaml
update:
  source: ""            # пусто = GitHub bolgov0zero/linager; "owner/repo"; либо URL зеркала с releases.json
  channel: stable
```

Зеркало (для закрытых сетей): каталог с файлами релизов и `releases.json` в формате GitHub API (`tag_name`, `prerelease`, `body`, `assets[].name/browser_download_url`), отданный по HTTP(S).

## Резервные копии
```bash
sudo linager backup --keep 7     # /var/backups/linager/linager-backup-<дата>.tar.gz (права 600)
```
В архиве: `db.dump` (pg_dump, формат custom), `config/server.yaml`, `data/` (ключи CA, сертификат и ключ подписи команд). **Архив содержит секреты, храните его так же бережно, как сервер.** Установщик включает ежедневную копию в 02:00 (`linager-backup.timer`, хранятся 7 последних).

Восстановление:
```bash
sudo linager restore /var/backups/linager/linager-backup-XXXX.tar.gz              # только база
sudo linager restore /var/backups/linager/linager-backup-XXXX.tar.gz --with-keys  # база и ключи (перенос на новый сервер)
```
Команда останавливает службу, заменяет содержимое базы дампом из архива **в одной транзакции**
(при любой ошибке база остаётся прежней) и запускает службу снова.
`--with-keys` возвращает в каталог данных ключи CA, сертификат порта клиентов и ключ подписи команд:
это нужно при переносе на заново установленный сервер, чтобы клиенты продолжили подключаться.
`server.yaml` из архива не восстанавливается (в нём пароль базы прежней установки), он лежит в архиве для справки.

## Ключ подписи (для владельца репозитория)
Ключ создаётся один раз: `minisign -G -W -p minisign.pub -s minisign.key`. Содержимое `minisign.key` кладётся в секрет репозитория `MINISIGN_KEY` (при защите паролем ещё `MINISIGN_PASSWORD`), строка из `minisign.pub` вписывается в `internal/release/release.go` (`PublicKey`) и `install.sh` (`PUBKEY`). Релиз без секрета публикуется как pre-release без подписи, такие релизы установщик и обновление отвергают.
